## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form payload -> booking API | Public users control every submitted field; the server must validate and derive pricing itself. |
| Landing handoff -> booking page | Query params and handoff state can be tampered with and must not be treated as trusted pricing or availability truth. |
| Booking API -> Neon | Lead, booking, and availability records must remain consistent even when requests race or fail halfway through. |

## STRIDE Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01-01 | Tampering | Booking payload | mitigate | Validate required fields server-side, derive price from server-side boat data, and reject invalid trip/date combinations. |
| T-03-01-02 | Denial of Service | Public booking endpoints | mitigate | Apply the existing rate-limit layer where credentials exist and fail soft in local/dev when Upstash is absent. |
| T-03-01-03 | Integrity | Boat availability | mitigate | Normalize day values consistently and enforce one row per boat/day before relying on DB-backed status. |
| T-03-01-04 | Spoofing | Fleet source of truth | mitigate | Establish a deterministic fleet sync path so the booking APIs do not depend on stale mock-only client data. |
</threat_model>
