## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Landing availability UI -> future booking system | Phase 2 can expose read-only data and modal state only. No booking payload may be persisted yet. |
| Search and filter input -> client rendering | FAQ search and boat filters are user-controlled and must only affect local rendering and read-only fetch params. |
| Third-party embeds -> browser | Footer maps and later chat-launch behavior must load lazily and never block the core landing experience. |

## STRIDE Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02-01 | Tampering | Availability modal placeholder | mitigate | Keep the modal purely client-side with a clearly labeled Phase 3 handoff CTA instead of any fake submit path. |
| T-02-02-02 | Information Disclosure | Crew and testimonial media | mitigate | Use approved marketing copy and placeholder Cloudinary assets only; no private contact data or hidden metadata may be embedded in assets. |
| T-02-02-03 | Denial of Service | Landing availability route | mitigate | Serve read-only mock payloads only, keep the route lightweight, and cap refresh frequency at 60 seconds or slower. |
| T-02-02-04 | Spoofing | FAQ chat CTA | mitigate | Emit a stable `gaff:open-chat` event in wave 2 so the later Botpress bridge can listen without the FAQ depending on future code. |
</threat_model>
