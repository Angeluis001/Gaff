## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser login form -> auth route | Email and password are fully user-controlled and must never bypass server-side validation or hash verification. |
| JWT session -> protected admin routes | Session claims are the only trust signal for admin access; route protection cannot rely on client-side checks alone. |
| Bootstrap path -> `admin_users` | First-user provisioning can create privileged accounts and must avoid accidental exposure in public routes or client bundles. |

## STRIDE Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01-01 | Spoofing | Admin credentials flow | mitigate | Verify credentials against `admin_users.password_hash` on the server with a modern password hash library and reject inactive users. |
| T-04-01-02 | Elevation of Privilege | Role-aware admin routes | mitigate | Persist `role` and `isActive` in JWT/session callbacks and enforce access in server helpers plus navigation filtering. |
| T-04-01-03 | Information Disclosure | Login UX | mitigate | Return generic sign-in errors and never reveal whether an email exists or a password was specifically wrong. |
| T-04-01-04 | Tampering | First-admin bootstrap | mitigate | Keep bootstrap logic in a server-only helper or script, guarded by environment variables or explicit execution flow, never a public GET route. |
</threat_model>
