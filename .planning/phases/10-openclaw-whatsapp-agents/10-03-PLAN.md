<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OpenClaw → /api/channels/openclaw | Inbound webhook: signed with OPENCLAW_WEBHOOK_SECRET |
| /api/channels/openclaw → GPT-4o | Customer message passed as role=user, not injected into system prompt |
| GPT-4o → escalate_to_human tool | Agent decides to escalate; ADMIN_WHATSAPP_NUMBER is env var, not from user input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-07 | Spoofing | Unauthenticated POST to /api/channels/openclaw | mitigate | verifyOpenClawRequest() checks OPENCLAW_WEBHOOK_SECRET on every inbound request (confirmed in source line 16 of route.ts). Check 1 in Task 1 verifies it returns 401 in production. |
| T-10-08 | Spoofing | WhatsApp number spoofing to trigger admin escalation alert | mitigate | ADMIN_WHATSAPP_NUMBER is read from Vercel env var, not from inbound payload. Attacker cannot redirect escalation alerts by manipulating the webhook body. |
| T-10-09 | Tampering | Prompt injection via customer WhatsApp message content | mitigate | Customer message is appended as `{ role: "user", content: userMessage }` in apiMessages array. The system prompt is constructed from env/code only — buildSystemPrompt(leadName, today) — and leadName comes from the DB lead record, not the raw message. Verified in chat-agent.ts lines 258–262. |
| T-10-10 | Denial of Service | Runaway GPT-4o tool call loop via adversarial message | mitigate | Tool call loop is capped at 4 rounds (chat-agent.ts line 268). After 4 rounds, fallback reply is returned without further API calls. |
| T-10-11 | Information Disclosure | Agent reveals internal system prompt via injection | accept | GPT-4o is instructed via system role message; the system prompt contains only business info (pricing, fleet). No secrets or env vars are in the system prompt. Low risk — fallback is marketing info. |
</threat_model>
